# Renbee RFQ Pipeline. Technical Documentation

## Executive summary

### What this is

A small backend service that sits behind Renbee's Webflow site and
turns a homeowner's *"I'd like a quote for a heat pump / solar PV /
battery / solar thermal"* enquiry into a complete, installer-ready
Request for Quote (RFQ). The homeowner enters a postcode and picks
a technology, the service does the heavy lifting (looking up their
EPC, checking planning constraints, checking the grid, drafting the
prose) and returns a structured RFQ that an installer can quote
against directly.

It also produces a friendly plain-English explanation of the
homeowner's EPC findings to keep them engaged while they decide
which installer to talk to.

The prose in both outputs is generated by a small open-source
language model (Llama 3.2 3B), constrained by strict
no-fabrication system prompts. Everything else is deterministic
Python.

### The homeowner journey

![Workflow diagram. Yellow nodes are decisions, green are LLM moments, blue is the entry point, indigo are proxy EPC fallback paths, pink is the HITL handoff to the installer.](docs/workflow.png)

1. **Step 1. Postcode + technology.** Homeowner enters their UK
 postcode and the technology they're interested in. That's it.
 No house number upfront.

2. **Address resolution (automatic).** The service looks up the
 postcode in the official UK EPC register.
 - If the postcode has exactly one address: continue silently.
 - If it has several distinct addresses: ask the homeowner which
 one is theirs (dropdown).
 - If it has no EPCs at all: look at the geographically nearest
 postcodes and show the homeowner a few comparable properties
 to pick from ("which of these is most like your home?"). If
 even that fails, fall back to a 4-question manual form.

3. **Site intelligence (automatic).** In parallel, the service
 checks whether the property sits in a listed building,
 conservation area, Article 4 zone, AONB, World Heritage Site,
 or National Park. And (for London / East / South East) how
 much spare capacity is on the local electricity substation. The
 homeowner sees these as a "Site intelligence we checked for
 you" panel.

4. **Step 2. Short technology-specific form.** The homeowner
 answers a handful of questions specific to the technology they
 chose (e.g. for heat pump: emitter type, hot water cylinder
 space, external unit space, garden access).

5. **Recommendation summary (first LLM moment).** The service
 produces a short, friendly explanation of the homeowner's EPC
 findings. *"Your home is rated D, the official EPC suggests
 adding loft insulation and upgrading heating controls."*. And
 weaves in any relevant planning constraint as a heads-up.

6. **Installer selection.** The homeowner sees vendor cards and
 picks one. (Renbee handles the actual matching.)

7. **Installer-facing RFQ (second LLM moment).** The service
 produces a longer professional paragraph aimed at the chosen
 installer, summarising the homeowner's enquiry, property,
 technology requirements, and any site constraints. With
 missing fields explicitly marked "not specified" rather than
 guessed.

8. **Human-in-the-loop review → submit.** Renbee / support
 reviews the generated RFQ, edits if needed, then forwards to
 the installer.

### What changes on Renbee's Webflow site

The service exposes three HTTP endpoints. The Webflow embed JS
needs to call them in sequence:

- `POST /api/initiate` after Step 1 → returns the list of Step 2
 fields to render (or a "pick your address" prompt, or a "pick a
 comparable nearby property" prompt).
- `POST /api/generate` after Step 2 → returns the homeowner-facing
 recommendation paragraph.
- `POST /api/generate-rfq` after vendor pick → returns the
 installer-facing RFQ paragraph.

**Adding a new RFQ field never requires a Webflow change.** The
service tells the embed JS which fields to render in the response,
so the form layout is data-driven.

A reference single-file demo (`webflow_demo.html`) shows the
intended look and feel, served at `GET /demo`.

### Integration checklist for Renbee

1. **Decide hosting.** The thesis demo runs Llama 3.2 3B locally
 on a laptop. For production, switch to a hosted endpoint
 (Together AI, Replicate, or Fireworks all work, pennies per
 request, no infra burden). The code change is small. Only two
 functions in `generate_rfq.py` need to swap from local Llama
 to a hosted call.
2. **Decide session storage.** Currently sessions are held in
 process memory, which is fine for thesis demos but means a
 server restart kills any in-flight enquiry. For Renbee
 production, swap for Redis or a small Postgres / SQLite.
 Roughly 15 lines of code.
3. **Tighten CORS.** Currently `*` for development. Tighten to
 Renbee's domain before going live.
4. **Embed JS.** The Webflow side needs the JS that calls the
 three endpoints in sequence and renders the dynamic Step 2
 form from the response. Not yet written, the API contract is
 ready for it.
5. **HITL review UI.** Some form of "review and submit" surface
 for support / admin to edit the generated RFQ before it goes
 to the installer. Not yet built, thesis scope stops at
 generating the prose.
6. **Optional. Register UKPN API key** if Renbee wants the grid-
 headroom panel to work for London / East / South East
 postcodes. Free registration on UK Power Networks' open data
 portal.

### What's working today (demo-able)

These end-to-end paths all work in the demo right now:

- **EPC found**. Postcode resolves to a single address, full RFQ
 generated.
- **Multi-address postcode**. Homeowner picks from a dropdown.
- **No EPC + nearby comparables**. Homeowner picks from a "which
 of these is most like your home?" picker, OR averages across
 all nearby comparables.
- **No EPC and no comparables**. Falls through to a 4-question
 manual form.
- **Planning constraints**. Listed buildings, conservation
 areas, Article 4, AONB, WHS, National Parks all surface.
- **Grid headroom**. For UKPN territory (London, East, South
 East), the homeowner sees their nearest substation's demand
 and generation headroom with a RAG status.

## 0. Design at a glance

Five design choices drive the structure of the code:

1. **Two LLM moments, not one.** The homeowner-facing recommendation
 and the installer-facing RFQ are served by two separate system
 prompts (`RECOMMENDATION_SYSTEM_PROMPT` and `RFQ_SYSTEM_PROMPT` in
 `generate_rfq.py`). Bundling them would force one prompt to address
 two audiences, blur the strict-no-fabrication rule, and break
 evaluation: §III.5 of the thesis evaluates the two moments
 separately, so the runtime keeps them separate too.

2. **Layered responsibilities, no business logic in the API layer.**
 `app.py` only does request routing, session storage, and HTTP
 error translation. All EPC resolution, proxy fallback, field
 metadata, and prompt building live in dedicated modules so they
 can be tested in isolation and changed without touching FastAPI
 wiring.

3. **Proxy EPC fallback hierarchy (honesty about uncertainty).** When
 the homeowner's own EPC isn't usable, the pipeline tries
 progressively weaker proxies. Same-postcode aggregate, then
 nearby-postcode pick, then nearby-postcode aggregate. And tags
 each with an `epc_source` value that drives the LLM to soften its
 language. Last-resort fallback is a 4-question manual form (Case
 B). The pipeline never silently substitutes a stranger's home for
 the homeowner's own, the homeowner sees the comparator set and
 chooses how to relate to it.

4. **Failure-tolerant external data.** Every upstream API
 (`api.get-energy-performance-data.communities.gov.uk`,
 `postcodes.io`, `planning.data.gov.uk`,
 `ukpowernetworks.opendatasoft.com`) can disappear without
 500-ing the request. Each fetcher wraps its network call in a
 `try/except` that returns an empty/None default. The site-context
 panel can degrade to "no special constraints recorded" rather
 than block the RFQ pipeline.

5. **Single source of truth for fields** (`FIELDS` dict in
 `epc_to_rfq.py`). The same dict drives: which fields the API
 considers required, what Webflow renders in Step 2, what the
 completeness score uses as denominator. Adding a new field or
 technology is one edit, not five.

## 2. End-to-end flow (with exact call ordering)

```
[Webflow Step 1: postcode + technology]
         │
         ▼
   POST /api/initiate
         │
         ├── fetch_epc_data(postcode)            ┐
         │      └─ search_by_postcode             │ Either succeeds (≥1 EPC),
         │      └─ for each row:                  │ or returns count=0 and
         │            fetch_certificate(lmk-key)  │ falls through to proxy.
         │            _normalize_certificate      │
         │            _normalize_recommendations  ┘
         │
         ├── if count==0 and no use_proxy flag:
         │      fetch_epc_data_with_neighbour_fallback(postcode,
         │         target_count=5, max_neighbours=10)
         │      └─ find_nearby_postcodes(postcode, max_count=10)
         │           via postcodes.io /nearest, radius=2000m
         │      └─ iterate neighbours, accumulating EPCs until ≥5 or
         │         all 10 neighbours exhausted
         │      if ≥1 EPC found → HTTP 409 proxy_nearby_candidates
         │      if 0 EPCs found → fall through to Case B (manual entry)
         │
         ├── assemble_rfq_input(epc_data, user_form, ...)
         │      └─ if count>1 and house_number doesn't disambiguate →
         │         AmbiguousAddress → HTTP 409 ambiguous_address
         │      └─ build property / recommendation / technology sections
         │
         ├── build_site_context(postcode)        ┐ Wrapped in try/except;
         │      └─ fetch_planning_constraints     │ never blocks the
         │      └─ fetch_ukpn_constraints         ┘ request on failure.
         │
         ├── missing_fields(rfq_input)
         ├── completeness_score(rfq_input)
         │
         └── store session in _SESSIONS, return session_id + missing_fields
                    │
                    ▼
       [Webflow Step 2: tech-specific form rendered from missing_fields]
                    │
                    ▼
              POST /api/generate  (homeowner-facing recommendation)
                    │
                    ├── _merge_additional_fields into session
                    ├── re-check missing_fields → 422 if anything still missing
                    ├── _get_model_backend() → lazy load Llama on first call
                    └── generate_recommendation(rfq_input, tokenizer, model)
                          ├── build_recommendation_prompt
                          │     └─ minimal slice: property (6 fields) +
                          │        recommendation + planning constraints
                          ├── generate_output (max_new_tokens=400)
                          ├── parse_model_output (brace-depth JSON scan)
                          └── _extract_or_fallback (regex fallback)
                    │
                    ▼
       [Homeowner reads explanation, sees Vendor A / B / C cards]
       [Homeowner picks a vendor]
                    │
                    ▼
              POST /api/generate-rfq  (installer-facing prose)
                    ├── re-check missing_fields → 422 if not ready
                    └── generate_rfq_summary(rfq_input, tokenizer, model)
                          ├── build_rfq_prompt
                          │     └─ full _strip_nulls(rfq_input)
                          ├── generate_output (max_new_tokens=800)
                          └── same parse + fallback chain
                    │
                    ▼
       [HITL review by support / Renbee admin]
                    │
                    ▼
       [Submit to installer — out of thesis scope, Renbee handles]
```

### 3.1 `POST /api/initiate`

**Request body** (`InitiateRequest`):
```json
{
  "postcode": "E1 6AN",                  // required
  "technology": "heat_pump",             // required: heat_pump | solar_pv | battery | solar_thermal
  "house_number": "10",                  // optional pre-filter (exact whole-token match)
  "lmk_key": "1234-...",                 // optional, picks a candidate from a prior 409
  "use_proxy": false,                    // Layer 1: same-postcode aggregate
  "use_proxy_nearby_average": false,     // Layer 2 "use average of all"
  "proxy_postcode": "E1 7AB"             // Layer 2 "pick one" — paired with lmk_key
}
```

**Success response (200, `InitiateResponse`):**
```json

  "session_id": "uuid4",
  "epc_found": true,
  "auto_filled": { /* the property section */ },

    "common":   [ { "name": "...", "label": "...", "type": "select", "options": [...] } ],
```

### 3.4 `POST /api/save-rfq`

Persists the final, reviewer-edited RFQ to disk so Renbee can share it with the
installer. The reviewer's edits (RFQ prose + structured JSON) live in the
browser until this call, so the edited content is sent in the request body.

```json
// Request (SaveRFQRequest)
{ "session_id": "uuid4",          // optional, for traceability
  "rfq_summary": "<edited prose>",
  "rfq_input": { ...edited... } }
```
```json
// Success (SaveRFQResponse)
{ "saved": true,
  "filename": "renbee_rfq_E16AN_20260603-141245.json",
  "path": "rfq_outputs/renbee_rfq_E16AN_20260603-141245.json" }
```

Writes one combined JSON file under `rfq_outputs/`
(`{ rfq_summary, rfq_input, session_id, vendor_id, saved_at }`). Filename token
is the postcode (from `rfq_input.common.postcode`) else `session_id` else
`rfq`, plus a UTC timestamp. Does **not** require a live session (the client
holds the content); if the session exists, its stored `rfq_summary` /
`rfq_input` are updated to the edited version. A non-dict `rfq_input` is
rejected with 422 by the request model.

- Created by `/api/initiate`, keyed by `uuid.uuid4()`.
- Mutated by `/api/generate` (merges additional_fields + stores

 production, swap `_SESSIONS` for Redis (~15 lines, `app.py:141`).

## 4. EPC resolution algorithm

### 4.1 Single-postcode lookup (`fetch_epc_data`)

```python
1. GET /api/domestic/search?postcode={pc}&page_size=100&current_page=1
2. for each row in response.data:
     GET /api/certificate?certificate_number={lmk_key}
     _normalize_certificate(detail, search_row)
     _normalize_recommendations(detail)
3. Write result to output/{postcode}.json (cache)
4. Return { postcode, fetched_at, count, properties: [...] }
```

`_normalize_certificate` translates the new gov.uk snake_case + numeric-coded
schema back into the legacy hyphenated dict shape that
`epc_to_rfq.assemble_rfq_input` consumes. Code lookups
(`built_form`, `tenure`, `construction_age_band`, `main_fuel`,
`improvement_summary`, `property_type`) are cached per-process in
`_CODE_CACHE` to avoid hammering `/api/codes/info`.

### 4.2 Address disambiguation (`select_certificate` in `epc_to_rfq.py`)

When the postcode returns ≥2 distinct addresses, `assemble_rfq_input`
calls `select_certificate(properties, house_number, lmk_key)`:

1. **If `lmk_key` provided**: filter to that exact certificate. Done.
2. **If `house_number` provided**: filter to certificates whose
 address starts with `{house_number}` as a whole token. Exact match
 only. `"1"` does NOT match `"10"` or `"1A"`. If exactly one match
 remains, use it.
3. **Otherwise**: collapse to **distinct address tokens** (first
 address line). If exactly one distinct address, use any of the
 certificates (most-recent inspection). If multiple distinct
 addresses, raise `AmbiguousAddress(candidates=[...])`.

`AmbiguousAddress` is caught in `app.py:574` and translated to HTTP 409.

### 4.3 Two-layer proxy EPC fallback

#### Layer 1. Same-postcode aggregate (user-triggered)

**Trigger**: client receives a 409 ambiguous_address, user clicks
"Use street average estimate", client re-POSTs `/api/initiate` with
`use_proxy: true`.

**Logic** (`epc_to_rfq.build_proxy_property_section`):
- Aggregate ALL EPC certificates at the input postcode.
- **Mode** for categorical fields (`property_type`, `built_form`,
 `construction_age_band`, `epc_rating`, `current_heating_system`,
 `current_fuel_type`).
- **Median** for `floor_area_m2`.
- **Most-recent inspection** for fields like the EPC rating breakdown.
- Tagged `epc_source: "proxy"`, `proxy_comparator_count: N`,
 `proxy_postcodes: [input_pc]`.
- `proxy_confidence`: `high` (N≥5), `medium` (N≥2), `low` (N=1).

#### Layer 2. Nearby-postcode picker (interactive)

**Trigger**: input postcode has zero EPCs and caller has NOT set
`use_proxy: true` (Layer 1 is preferred when it's possible).

**Algorithm** (`fetch_epc_data_with_neighbour_fallback`):
```
target_count = 5
max_neighbours = 10

1. primary = fetch_epc_data(postcode)  (wrapped — 400/network errors → count=0)
2. if primary.count > 0: return primary  (Layer 2 not needed)
3. nearby = find_nearby_postcodes(postcode, max_count=10)
   └─ GET api.postcodes.io/postcodes/{pc}/nearest
      ?limit=11    (10 + 1 because index 0 is input itself)
      &radius=2000 (metres; postcodes.io maximum)
   └─ filter out the input postcode itself; return up to 10 neighbours.
4. accumulated = []
   for pc in nearby:
       data = _safe_fetch_epc_data(pc)
       if data.properties:
           accumulated.extend(data.properties)
           contributing.append(pc)
           if len(accumulated) >= 5: break    ← stops at target_count
5. return { count: len(accumulated), properties: accumulated,
            proxy_used: bool(accumulated),
            proxy_postcodes: contributing }
```

> **Important**: the stopping rule is "at least **5** properties accumulated,
> OR all 10 neighbours exhausted". The 5 is `target_count` in
> `epc_fetch.py:237`, the 10 is `max_neighbours` (== postcodes.io request
> limit). One neighbour can contribute multiple EPCs (a postcode with 8 flats
> on it counts as 8 toward the 5 target).

**Decision split** based on `accumulated` size:
- `>= 1` → HTTP 409 `proxy_nearby_candidates` with the candidate list
 (built by `build_nearby_candidate_list`. Each entry carries
 `lmk_key`, `postcode`, `address`, `inspection_date`, plus the four
 Case-B form fields so Webflow can render a comparison panel).
- `== 0` → fall through to Case B (manual 4-question entry).

The user makes one of two choices on the Layer 2 picker:

**Choice A. "Pick one as closest match"**: client POSTs
`/api/initiate` with `lmk_key` + `proxy_postcode`. Server re-fetches that
postcode, finds the chosen certificate, and builds a normal property
section from it via `build_picked_property_section`. Tagged
`epc_source: "proxy_nearby"`, `proxy_picked: true`,
`proxy_comparator_count: 1`, `proxy_confidence: "low"`,
`proxy_postcodes: [chosen_postcode]`. Recommendations come from that
single EPC but are tagged `recommendation_source: "proxy_aggregate"`
so the LLM still softens the language.

**Choice B. "Use average of all 5"**: client POSTs with
`use_proxy_nearby_average: true`. Server re-runs
`fetch_epc_data_with_neighbour_fallback` and aggregates exactly like
Layer 1 (mode/median/most-recent), but tags as `epc_source: "proxy_nearby"`.

**Layer 2 is bypassed** when the caller already set `use_proxy: true`
(`app.py:524`). We don't expand search radius behind the user's back.

### 4.4 Three proxy phrasings (LLM prompt distinguishes)

These tags drive the LLM's "softening" language:

| `epc_source` | `proxy_picked` | LLM phrasing |
|---|---|---|
| `"epc"` |. | "your EPC says…" |
| `"proxy"` |. | "based on similar properties on the same street" |
| `"proxy_nearby"` | `true` | "based on a nearby property the homeowner indicated is similar" |
| `"proxy_nearby"` | `false/unset` | "based on similar properties in nearby postcodes" |

Defined in both `RFQ_SYSTEM_PROMPT` and `RECOMMENDATION_SYSTEM_PROMPT`
(see `generate_rfq.py:35` and `:70`).

## 5. Field metadata & completeness scoring

### 5.1 `FIELDS` dict

Single source of truth in `epc_to_rfq.py`. Structure:

```python
FIELDS = {
    "common": {
        "preferred_contact_method": {
            "label": "How would you prefer to be contacted?",
            "type": "select",
            "options": ["email", "phone", "either"],
            "required": True,
        },
        "technology_requested": { "required": True, ... },
        # ... more
    },
    "property": { ... 13 fields ... },
    "heat_pump": { ... },
    "solar_pv": { ... },
    "battery": { ... },
    "solar_thermal": { ... },
}
```

**Adding a new field**: declare it in the relevant section. No other
changes needed for `assemble_rfq_input` or `missing_fields`. Webflow
embed JS reads `missing_fields` so the UI updates automatically.

**Adding a new technology**: declare the section dict plus add one
entry to `_TECH_SECTIONS`. `app.py:455` reads `_TECH_SECTIONS` for
validation of the `technology` request field.

### 5.2 `missing_fields(rfq_input)`

Returns `{ section: [field_specs...] }` for every field where
`required: True` AND the value is missing. Used:
- by `/api/initiate` to drive Step 2 form rendering,
- by `/api/generate` and `/api/generate-rfq` as a pre-flight check
 (422 if anything required is still empty).

**Always emitted**: required `common` fields and technology-specific
fields. The `property` section is required when EPC was NOT found AND
not in proxy mode (Case B → 4-question form), EPC-found and proxy
modes auto-fill `property`.

### 5.3 `completeness_score(rfq_input)`

```python
{ "populated": int, "required": int, "score": float }
```
This is the **§III.8 completeness metric** for RQ2. `score = populated /
required`. Returned on every API response.

### 5.4 Per-technology field sets (and where the questions come from)

Every form is assembled as **common + property + one technology section**. The
common and property sections are reused verbatim for all four technologies
(single source of truth in `FIELDS`), so the four forms share the bulk and
differ only in the final technology block. In the no-EPC manual case this is
why the forms look ~70% identical: the same 7 required common/property fields
are always shown, and only the technology section changes.

**Required fields that differ by technology:**

| Technology | Required technology questions | What it is really asking |
|---|---|---|
| Heat pump (4) | heat emitters, hot water cylinder space, outdoor unit space, garden / side access | Can we fit an outdoor unit and distribute the heat? (replacing the heating system) |
| Solar PV (3) | roof orientation, usable roof area, shading | How much electricity can the roof generate? |
| Battery (4) | existing / planned solar PV, battery purpose, backup-power need, install location | How will the battery be used and where does it go? |
| Solar thermal (6) | roof orientation, usable roof area, shading, **plus** hot water cylinder space, occupants, bathrooms | Roof potential **plus** how much hot water the household uses |

Solar PV and solar thermal overlap (both roof-mounted, both ask orientation /
area / shading). Solar thermal adds hot-water-demand questions (cylinder,
occupants, bathrooms) because it heats water rather than generating
electricity, so sizing depends on household hot-water use. That is why its form
is the longest.

**Where the questions come from:**

- **Property section** mirrors the **UK EPC certificate fields**
  (property_type, floor area, heating, fuel, walls, roof, windows, etc.), so an
  EPC lookup auto-fills them one-to-one.
- **Technology sections** are informed by the **MCS 2025 installation
  standards** (the standards an MCS-certified installer designs and quotes
  against): MIS 3005 heat pump, MIS 3002 solar PV, MIS 3012 electrical energy
  storage (battery), MIS 3001 solar thermal. The questions capture what those
  standards need for a site assessment.
- **Common section** is standard enquiry / lead fields (contact method,
  timeline, motivation, optional budget and notes).

None of this is fetched at runtime. The field sets are hand-authored in the
`FIELDS` dict, grounded in the EPC schema and the MCS standards above.

### 5.5 Asked vs available fields (deliberate simplification)

Each `FIELDS` entry carries a `required` flag. `missing_fields()` only surfaces
`required: True` entries, so the homeowner-facing form is kept short. Fields
with `required: False` still exist in the schema (the LLM uses them if present,
and the property ones auto-fill from the EPC), but they are never rendered as a
question. So "available but not asked" simply means `required: False` in the
dict (for example `current_water_heating_type` at `epc_to_rfq.py` is
`required: False`, which is why it never appears in the solar thermal form).
This is a deliberate "keep the form human" choice, not a gap.

**Shared on every technology**

- Common — asked: technology, contact method, timeline, motivation. Available,
  not asked: budget_range, additional_notes.
- Property — asked: property_type, floor_area_m2, current_heating_system,
  current_fuel_type. Available, not asked (auto-filled from EPC when found):
  built_form, construction_age_band, hot_water_system, walls_description,
  roof_description, windows_description, occupancy_status, access_constraints.

**Per technology** (asked = required, shown in the form):

| Technology | Asked (required) | Available but not asked (`required: False`) |
|---|---|---|
| Heat pump | emitter_type, hot_water_cylinder_space_available, external_unit_space, garden_or_side_access | heat_pump_type_interest, radiator_suitability_known, insulation_status_basic, boiler_age_years, noise_or_planning_constraints, bus_interest, cooling_interest |
| Solar PV | roof_orientation, usable_roof_area_m2, roof_shading_level | roof_type, roof_pitch, roof_condition, number_of_roof_faces, annual_electricity_bill_gbp, daytime_electricity_usage, battery_interest, ev_present_or_planned, roof_under_warranty |
| Battery | existing_solar_pv, battery_purpose, backup_power_required, battery_location_preference | existing_solar_pv_capacity_kwp, desired_capacity_band, annual_electricity_bill_gbp, daytime_electricity_usage, ev_present_or_planned, time_of_use_tariff |
| Solar thermal | roof_orientation, usable_roof_area_m2, roof_shading_level, hot_water_cylinder_space_available, number_of_occupants, number_of_bathrooms | current_water_heating_type, existing_cylinder_size_litres, roof_type, roof_pitch, roof_condition, collector_type_preference, auxiliary_heating_intended |

To ask one of the optional fields, flip its `required` flag to `True` in
`FIELDS` and it appears in the form automatically (no Webflow change). The form
was kept to the required set on purpose, to stay short and human to fill in.

## 6. Site context enrichment (`build_site_context`)

> **Current status (2026):** the grid subsection below (6.2) is documented as designed but is **not functional today** — UKPN retired the `dfes-network-headroom-report` dataset, so `site_context.grid` is `null` for every postcode. Listed-building detection (via a postcode-centroid lookup) also almost never resolves, so in practice only conservation areas, AONBs, WHS, National Parks, and Article 4 are surfaced. See §12.

Always called on `/api/initiate`. Independent of EPC outcome. Wrapped in
`try/except` (`app.py:591`) so an upstream failure never blocks the RFQ
pipeline.

### 6.0 Planning vs grid: what each one affects

The two site-context sources answer two different questions about the same
install:

- **planning.data.gov.uk = "Are you allowed to install it, and what
  permission do you need?"** This is about the building and its location
  (heritage and visual rules).
- **UKPN grid headroom = "Can the local electricity network physically
  handle it?"** This is about spare capacity at the nearest substation.

One is about permission, the other is about power. They are independent. An
address can have a planning constraint with no grid issue, or a grid
constraint with no planning issue.

**Planning flags** affect permission, timeline, and where equipment can sit:

| Flag | Effect on the install | Example |
|---|---|---|
| Listed building (Grade I / II* / II) | Needs Listed Building Consent for external kit, can be refused on heritage grounds | Grade II cottage: the heat pump outdoor unit or roof panels need a consent application before work starts |
| Conservation area | Permitted Development restricted, visible / street-facing equipment likely needs planning permission | Bath (`BA1 1LZ`): panels on the front roof slope probably need consent, rear roof may be fine |
| Article 4 direction | Council has removed specific PD rights, so normally-automatic work now needs an application | Borough / Southwark (`SE1 9SG`): even a modest external unit may need permission |
| AONB / National Park / World Heritage Site | Extra visual / landscape sensitivity, visible equipment assessed for impact | Cotswolds AONB (`OX7 3EL`): panels judged on visibility |

Effect: a planning flag usually means more time (an application is weeks to
months plus fees) or repositioning the equipment, rather than blocking the
technology outright.

**UKPN grid headroom** has two numbers, and which one matters depends on the
technology:

- **Demand headroom** = spare capacity to draw power. Matters for things that
  add load (heat pumps, EV chargers). A heat pump adds roughly 3 to 9 kW of
  winter load. Lots of headroom (Green RAG) connects with no fuss, near
  capacity (Red) may require a network upgrade or a limited connection.
- **Generation headroom** = spare capacity to export power. Matters for things
  that push power back (solar PV, exporting batteries). Low headroom can mean
  an export cap (G98 / G99 limits) or export refused, so the system is sized
  smaller or pairs with a battery for self-consumption.

Effect: grid headroom affects connection approval, possible export limits, and
whether a costly grid reinforcement or delay is needed.

**By technology** (the clearest way to see the split):

| Technology | Planning matters because... | Grid (UKPN) matters because... |
|---|---|---|
| Heat pump | outdoor unit is visible (consent in listed / conservation) | draws extra power, so **demand** headroom |
| Solar PV | roof panels visible (consent in conservation / AONB) | exports power, so **generation** headroom |
| Battery | usually internal / garage, rarely a planning issue | charges / exports, so mostly **generation** headroom |
| Solar thermal | roof panels visible (consent in conservation / listed) | **basically irrelevant**, heats water with no real grid impact |

That last row is the cleanest illustration: solar thermal can have a planning
issue but essentially no grid issue, while a heat pump in a non-protected
modern house may have no planning issue but a grid one if the substation is
full. The two checks are genuinely separate, which is why the pipeline runs
both and surfaces them together in the "Site intelligence" panel. The LLM
prompts reflect the split: for heat pump enquiries they cite demand headroom,
for solar PV / battery they cite generation headroom (see §7.4).

### 6.1 Planning constraints (`fetch_planning_constraints`)

1. Resolve postcode → (lat, lon) via `postcodes.io/postcodes/{pc}`. Cache.
2. For each of 6 datasets, hit
 `GET https://www.planning.data.gov.uk/entity.json?latitude={lat}&longitude={lon}&dataset={ds}&limit=5`.
3. Datasets queried (in this exact order):
 - `listed-building`
 - `conservation-area`
 - `article-4-direction-area`
 - `area-of-outstanding-natural-beauty`
 - `world-heritage-site`
 - `national-park`
4. For each, if any entities are returned, mark the corresponding flag.
5. Listed-building grade comes from `first.get("listed-building-grade")`
 (note hyphens. Planning.data.gov.uk's convention).
6. Failure-tolerant: timeout or non-200 yields an empty dict per dataset,
 not an exception.

**Returned shape** (always all 7 keys):
```python
{ "listed_building": bool,
  "listed_grade": "I" | "II*" | "II" | None,
  "conservation_area_name": str | None,
  "article_4": bool,
  "aonb_name": str | None,
  "whs_name": str | None,
  "national_park_name": str | None }
```

### 6.2 UKPN grid headroom (`fetch_ukpn_constraints`)

Returns `None` (silently) when:
- `UKPN_API_KEY` is not set, OR
- postcode → lat/lon fails, OR
- no PRIMARY substation within 5 km (i.e. not UKPN territory. UKPN
 covers London / East / South East only).

**Two queries** against `dfes-network-headroom-report`:

```python
# 1. Nearest PRIMARY substation, Counterfactual scenario, this year, Demand
where = (
  "within_distance(spatial_coordinates, geom'POINT({lon} {lat})', 5000m)"
  " and physical_level='PRIMARY' and scenario='Counterfactual'"
  " and category='Demand Headroom' and year=date'2026'"
)
order_by = "distance(spatial_coordinates, geom'POINT({lon} {lat})') asc"
limit = 1

# 2. Generation inverter headroom at the same substation_name
where = (
  "substation_name='{name}' and scenario='Counterfactual'"
  " and category='Gen inverter headroom' and year=date'{year}'"
)
limit = 1
```

`year` defaults to `"2026"` (parameter on `fetch_ukpn_constraints`).
Scenario is hard-coded to `"Counterfactual"` (the do-nothing baseline.
most defensible default for thesis claims).

**Auth header**: `Authorization: apikey {UKPN_API_KEY}`.

**Returned shape** (or `None`):
```python
{ "licence_area": "EPN" | "LPN" | "SPN",
  "primary_substation": "Tooley St",
  "demand_headroom_mw": 12.6,
  "demand_headroom_percent": null,         # often absent on this dataset
  "demand_rag": "Green - ...",
  "generation_headroom_mw": 42.82,
  "year": "2026",
  "scenario": "Counterfactual" }
```

**Output shape**: `{ "rfq_summary": "<one paragraph>" }`

`_strip_nulls`.

**Strict rules**:
- ONLY use provided data, missing → "not specified".
- Render underscore-coded values in natural English

- Match prose to `common.technology_requested`. Don't mention other

- Mandatory mentions when `site_context` flags are set:
 - listed_building → grade + listed building consent.

 - article_4 → flag that specific PD rights are removed.
 - aonb / whs / national_park → heritage / landscape sensitivity.
 - grid (UKPN): demand headroom for heat pump, generation headroom for
 solar PV / battery.
- Single fluent paragraph. NOT a list, NOT nested JSON.

### 7.5 Parser chain (`parse_model_output` + `_extract_or_fallback`)

Smaller models occasionally emit weird shapes. The parser handles four
failure modes:

```
ok               → JSON parsed cleanly, key present, string value
nested_unwrapped → model double-wrapped: {"rfq_summary": "{\"rfq_summary\": \"...\"}"}
regex_fallback   → JSON parse failed, but a "rfq_summary": "..." pair
                   could be extracted via regex (with markdown fence
                   stripping)
raw_fallback     → all above failed; raw text returned so UI isn't blank
                   (`parse_status` surfaces this to the debug panel)
```

`parse_model_output` does a **brace-depth scan** over the raw output
to find every balanced `{...}` block, then tries each one as JSON in
order. This is more robust than `re.search(r"\{.*\}", ..., re.DOTALL)`
because it handles nested braces correctly.

## 9. Error handling philosophy

- **Upstream failures should never 500 the request**. Wrappers:
 `_safe_fetch_epc_data`, `try/except` in `fetch_planning_constraints`
 / `fetch_ukpn_constraints` / `_planning_query` / `_ukpn_query` /
 `_resolve_latlong` / `find_nearby_postcodes`. Each returns an
 empty/None default on failure.
- **`build_site_context` is wrapped in `try/except`** at the call site
 (`app.py:591`). Worst case the panel shows "no special constraints
 recorded."
- **The EPC fetch itself** is wrapped (`app.py:516`) when called from
 `/api/initiate` so a bad postcode (gov.uk returns 400) falls into
 the proxy / Case B path instead of 500-ing.
- **AmbiguousAddress** and `proxy_nearby_candidates` are explicit
 business-logic 409s, not errors.
- **422** is reserved for "still missing required fields" (client
 contract violation. Webflow should have sent everything).
- **`unknown_session`** = 404 (session expired or never existed).
